## v0.21.0 - 2026-10-31
### Added
* `RUNNER_ZIG_SEED=<version>=<sha256>` (off when unset): the runner builds a Zig global-cache seed in the engine, from only the pinned Zig tarball and a `build.zig` it writes, and gives it to the Zig cache volume of every job that runs Zig. A new volume starts from the seed (`withMountedCache(source:)`) and an existing one gets what it lacks (`cp -an`, manifests last). No job compiles Zig 0.17's build runner itself any more: a cold `zig build test` of zig-runner went from 146 s to 49 s on the laptop. Jobs without Zig send the same documents as before.
* The runner pre-warms the engine in the background (`RUNNER_PREWARM`, on by default): it builds the default image's provisioned base container, and the Zig cache seed with `RUNNER_ZIG_SEED`, with no job, when the pool starts, when the engine starts again (seen by the memory gate's engine detector where the engine's cgroup is visible, else by its unix socket appearing or being replaced) and after a job that had to wait for the engine. The documents are written by the job's own writers, so the engine answers the first job from its cache: on the laptop that job had spent 169 s in "Set up job" after an engine wipe. The warm takes a memory-gate slot of its own once the engine accepts its session, mounts no volume, logs `pre-warm: base container ... built in N s (<image@digest>)`, can be cancelled by a stop, and never fails or blocks a job. Skipped with `RUNNER_ENGINE=cli` and when the runner trusts no ref.
### Changed
* The README and the proofs' "Against today's code" table now say that the tool cache and the package download caches are the runner's own cache volumes, outside every step's key, with mount-blindness assumed: a step that installs a tool into the tool cache itself and is replayed after the volume was pruned leaves a later step a PATH to a directory that is gone.
* The proofs' README and the Lean docstrings no longer credit BuildKit with leaving cache volumes out of a step's key: since Dagger v0.21.0 an exec is reused by DagQL's recipe digest, in which a cache volume is its key string, namespace, sharing and owner and never its content. No theorem changed. The `Key` row now spells out that the volume's identity (repository and trust scope) is in the real key, the one-time miss a change of trust scope costs, that the provisioned base container is today's one cross-scope seed, and that a seeded volume may only come from a trusted, pinned input.
* The from/ZIG_LOCAL_CACHE_DIR and provisioning nodes of the base container, and the wait for a starting engine, are each written by one function (`writeFrom`, `writeProvision`, `openSessionWaiting`), ahead of the base-container pre-warm that will use them; documents and behaviour unchanged.
### Fixed
* A step that prints a lot no longer has its last lines logged after the next step has started, and an `::add-matcher::` or `::add-mask::` near the end of its output now applies to the steps after it instead of being lost (#140): once a step's live output has started, the runner reads it up to the step's end before collecting its result, waiting while lines keep coming and warning in the step's log if they stop for 5 s or take over 2 minutes.
* With step caching, a failed step whose record lacks the marker saying which job ran it (its file commands cut short by a full disk, or never written because the step killed its own shell) is no longer replayed as this run's failure: unless the step showed it ran in this job, it runs again, as a failure the cache kept from an earlier run does (#69).
* With step caching, a cached step inside a composite action is replayed, its log, masks, outputs and state included, even while the previous inner step's last live lines are still arriving: the runner no longer takes them for the cached step's own. And a line one inner step replayed no longer swallows the same line printed live by a later one.
* With output keys, pruning the output store no longer deletes a stored output in place while another job is copying it into its next step, which could leave that step starting from part of the output: a pruned directory is renamed out of the way first, and the copy fails, falling back to the step's own container, if its directory went during it.
* The memory gate no longer charges the engine for reclaimable slab (`memory.stat slab_reclaimable`, the kernel's dentry and inode cache: 180-270 MB on razorbill at idle, where the gate charged 1.3 GB for an engine whose own heap was about 650 MB). The kernel drops it as cheaply as the inactive file cache already left out, so a runner was held, and a job's learned size raised, for memory the engine gives up the moment a job needs it. Active file pages stay counted, since dropping them means reads from the SD card. `docker stats` still shows memory.current less inactive_file, so it reads that much higher than the gate's log.
### Security
* A `run:` step's working directory holding a secret, its own `working-directory:` or the one `defaults.run` gives it, now reaches the step as a Dagger secret, instead of in plain text in the command the engine keeps in its cache metadata, and the step runs every time, as one using a secret does.
* A job's log spool is no longer made by name in a shared `/tmp` (#106). The runner makes its own directory under `RUNNER_LOG_SPOOL_DIR`, `zig-runner-<uid>`, mode 0700, once at startup, and uses one already there only if it is a directory (not a symlink), owned by the runner's user and closed to everyone else. Each job's `zig-runner-job-<id>.log` is created in it exclusively with mode 0600, so a file or symlink planted at that name is refused rather than followed or written through (the job then keeps its log in memory, and says so). This makes running the runner by hand as safe as under the systemd unit's `PrivateTmp`. The file is still removed when the job ends.
* Steps get the Dagger engine (`RUNNER_DAGGER_NESTING`) only in jobs the runner vouches for: a step's own Dagger client could open any cache volume by its key, so a pull request, a job from a ref or event outside the trusted lists, or any job on a `*` runner could write the caches and output-key store trusted jobs read. In those jobs, "Set up job" says Dagger in steps is off, and a failed step that names Dagger is told why.
* The busybox the runner puts into job containers, which Docker actions, service containers and output keys run their scripts with, is pinned by digest (`busybox:1.37.0-musl@sha256:f6a95d61...`, the multi-arch index, so one pin serves amd64 and arm64) instead of a tag its owner could move. Renovate moves the pin (a new busybox version in a pull request of its own, a rebuilt image's digest monthly at most), and CI checks on every pull request that the pin is a pullable index with the applets the runner uses (`.github/scripts/busybox-pin.sh`). Docker actions, service containers and output-keyed steps run once more after upgrading, and after each busybox update, as the busybox file's key changes.
