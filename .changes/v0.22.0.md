## v0.22.0 - 2026-11-01
### Added
* Zig's local cache volume (`RUNNER_ZIG_LOCAL_CACHE`) stays under `RUNNER_ZIG_LOCAL_CACHE_MAX_MB` (4096 by default; 0 for no limit). It grew by about 111 MB for every commit built, 5.7 GB after 50 jobs on the laptop. Before each job, a container of its own starts the cache over, whole, in a new generation of the volume once the live one is past the limit, and removes a generation 6 hours after its successor became current; jobs see the live one through one fixed path (`.../zig-local/current`), so no step's cache key changes. A roll that fails is logged and the job goes on.
* The runner can register and remove its self-hosted runners as a GitHub App instead of with GH_TOKEN: GH_APP_ID (the App ID or Client ID), GH_APP_PRIVATE_KEY_FILE or GH_APP_PRIVATE_KEY (PKCS#1 or PKCS#8 PEM), and optionally GH_APP_INSTALLATION_ID, else looked up from GH_SCOPE. It signs the App JWT natively, caches the hour-long installation token, and mints a new one 5 minutes before expiry or after a 401. GH_TOKEN and the App exclude each other; the runner refuses to start with both or neither.
### Changed
* CI's "Format, build and test" job runs `zig build test -j1` on an ARM64 self-hosted runner (the Pi), so Zig compiles the tests and the runner one after the other instead of side by side. Measured on razorbill, the two compiles peak at about 947 MB and 890 MB, so together a job raised the engine by about 1.7 GB, and two jobs (about 4.2 GB) went over its 4 GB cap and ran one at a time. One at a time a job peaks at about 1 GB, so two fit in about 3.5 GB: each takes about 25 s longer (81 s instead of 56 s), and the pool finishes about 38% more. GitHub's runners and x86_64 self-hosted runners build as before.
* Steps no longer get the job's Dagger engine by default (`RUNNER_DAGGER_NESTING` is now off). A step with it could open any cache volume by its key and run privileged containers, which is control of the machine, so it also defeated the check that a tool tree in a cache volume is the runner's own. To turn it back on for a pool whose trusted jobs run `dagger call` inside a step, set `RUNNER_DAGGER_NESTING=true` (or `--dagger-nesting=true`); it is still given only in jobs the runner vouches for (#230). The runner logs `Dagger in steps: on` or `off` at startup, next to what it trusts.
### Fixed
* The test suite takes about 16 s to run instead of about 37 s (`zig build test`, warm, on the laptop), and every test asserts what it did. A step none of whose lines arrived is no longer waited for once the log stream has ended, and the fake Dagger session ends its stream at once: every job test waited 60 ms per step for lines that could not come. The test of a live line without its end marker waits 50 ms for the rest instead of 5 s, and the two slow-engine cases run side by side.
* About a third of steps no longer end ~100 ms late. A step's `end` marker is now echoed straight after the step, before the script's own bookkeeping (the file commands touched and combined, the script file removed). That bookkeeping started eight processes (~20 ms) between the step's last line and the marker, so the engine's log export, in batches about 100 ms apart, often delivered the marker one batch after the step's output, and the runner waited for it after the exec had already answered. The bookkeeping prints nothing, so the marker still follows every line of the step. The script text is part of every step's cache key, so the first run after the upgrade replays nothing.
* A pre-warm that found everything in the engine's cache (under 3 s) no longer teaches the memory gate its estimate for `zig-runner pre-warm`, as a job that replayed steps does not. On razorbill a warm right after a restart, with the other instance having warmed the shared engine, took 0.4 s and was learned at 0 GB against 1.3 GB cold, so the warm after the next engine wipe would have been admitted with nothing reserved.
* A job mounts only the package-cache volumes of the tools its `run:` scripts and actions name (npm, pip, uv, cargo, go, Gradle, Maven and the rest), the tool cache when it uses an action, and Zig's as the Zig cache seed decides, instead of all sixteen. Turning the mounts off measured 24 ms of wall time and 45 ms of engine CPU per step on the laptop, about a quarter of a trivial step's engine CPU. A tool the heuristic misses only starts with a cold cache; a job that names every tool mounts exactly what it did.
* A step replayed from the cache right after another replayed step is one query instead of two: its recorded output is asked for in the exec's own query, where it used to be sent again for it. A replayed step cost 97 ms on the laptop, largely that second round trip. The output shown is still exactly what was recorded; one past 4 MiB is still not read, and a step that turns out to run shows only its live log.
* The test suite takes about 1.3 s less to run (`zig build test`, warm, on the laptop), and every test asserts what it did, with the same deadlines and inputs. Independent slow cases now run side by side: the two 70000-deep YAML inputs, the two interpolation limit cases, the PostgreSQL client's silent connect and silent statement, and the database writer's queued-at-once case beside its 2 s connect timeout.
* The runner no longer checks every 10 ms for a step's end marker: the log reader wakes it when a line, the marker or the end of the stream arrives, which cost a step about 5 ms on average. The waits are bounded as before: 60 ms for a first line, 5 s between lines, 2 minutes in all.
* Install Zig no longer re-reads the cached Zig tree (19,500 files, 309 MB; 10-19 s on razorbill under load) when the runner has already checked it. In "Set up job", before any step runs, the runner checks every tree in the tool cache (TOOL/VERSION/NAME). It re-hashes only the files whose size, inode, mtime or ctime changed, using lists kept in a volume that no step ever mounts, so a job cannot forge them. It then gives steps each tree's path and digest in `ZIG_RUNNER_TOOL_TREES`, and install-zig.sh skips its own check only when that variable names its tree with the pinned digest. Anything else means the full check, as on GitHub's runners. The check is skipped in jobs that have Dagger nesting, whose steps could reach the volume, and `RUNNER_TOOL_TREES=false` turns it off.
### Security
* The default job image, the shared base of every job across trust scopes, is pinned by its Docker Hub multi-arch index digest (`ubuntu:24.04@sha256:fe81560990fae86dc4743202b2cb4d3df98d0bcf949173cecef15ce1127ef852`, one pin for amd64 and arm64) instead of the moving tag the pre-warm rebuilt from at every boot. Renovate moves the pin monthly and CI's `ubuntu-pin.sh` checks it. After upgrading, every step re-keys once, because the base image's identity changes, and runs once more; the tool cache keeps its volume, as it is keyed by the image's name. A config or `container:` naming `ubuntu:24.04` gets the pinned, provisioned image; another digest is used as is. Provisioning's apt packages still come from the archive on the build date (`pkg=version` pins vanish from noble-updates within weeks, and snapshot.ubuntu.com does not serve arm64), so the pre-warm's line now names the provisioned seed by a fingerprint of its installed packages.
* Zig's global cache is no longer shared between jobs, and seeding it is on by default, from signature-verified Zig releases. Zig runs the compiled outputs it finds in `o/` without checking them, so one compromised job in a trust scope could plant a binary or object that every later Zig job in that scope linked or ran. Each job now gets the seed as a directory of its own container, or an empty cache without one, and what it writes there is gone when it ends. Only the package tarballs (`p/`), which Zig hashes again when it unpacks them, stay shared, in a new volume (`.../zig-packages`). The runner seeds the releases in `RUNNER_ZIG_SEED_VERSIONS` (by default the Zig it is built with) and the Zig versions its tool-cache check finds in `repo` jobs' tool caches, at most 3 in all. Before seeding from one it checks each tarball's minisign signature and trusted comment natively against Zig's pinned public key, and a release that does not verify is not seeded, which "Set up job" says. `RUNNER_ZIG_SEED=<version>=<sha256>` still pins one release by digest. Zig's local cache volume (`RUNNER_ZIG_LOCAL_CACHE`) is now kept only for `repo` jobs; an untrusted job's is its own, and "Set up job" says so.
