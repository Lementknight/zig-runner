## v0.23.0 - 2026-11-01
### Fixed
* Runners that share one Dagger engine pre-warm it one at a time. Two pools started together (razorbill's two systemd units) both built the base container and the Zig seed at once, 205 s each, doubling the startup CPU and memory: the engine does not merge two identical builds. Each warm now takes a lock on the directory of the engine's unix socket, which every runner of the engine can open under systemd and compose alike, and the next logs "pre-warm waiting for another runner's warm on this engine", then finds it all cached. A stop ends the wait, and a runner that dies releases the lock.
* Every job mounts the tool cache again. v0.22.0 mounted it only for jobs whose workflow names it or uses an action, so a step that installs into it from a script file (zig-runner's own `install-zig.sh`) found no `/opt/hostedtoolcache` and failed: the step user cannot make it. The package managers' caches stay mounted on demand, where a miss only costs a cold cache.
* Four behaviours now match GitHub's runner (#214). A step's own `env:` no longer changes the variables GitHub sets again over it (`GITHUB_SHA`, `RUNNER_TEMP`, `GITHUB_ACTIONS` and the rest), in the process; `${{ env.X }}` still reads the step's value. A step failed only by a workflow or file command (a refused `::set-env`, a malformed `$GITHUB_OUTPUT`) no longer also logs "Process completed with exit code 1.". In a composite action's `run:` steps, a `shell:` or `working-directory:` expression that cannot be evaluated fails the step instead of being used as written. A `::` command keeps trailing whitespace in its data, and its property names match in any case (`FILE=`, `Title=`), with the last of a name winning.
* Step caching: a replayed step whose $GITHUB_PATH entry or $GITHUB_ENV value names a directory in the tool cache that "Set up job" found no tree holding (the volume was pruned or wiped since the recorded run, or the trees were not checked) runs again instead of pointing PATH at a directory that may be gone (`protoc: not found`). A replay whose directory lies in a tree "Set up job" checked still stands (#229).
* A `run:` step's script file is named as GitHub's runner names it (#214): `.sh` for `bash` and `sh`, `.py` for `python`, in any case, and no extension for any other program as written, `python3 {0}` and full paths such as `/bin/bash` included. A traceback or `$0` now shows the same file name as on GitHub. This reverses #196's choice to recognise those by their base name. Steps with such a shell get a new cache key and are not replayed the first time they run after the upgrade.
* The README says how merges are checked as #104 decided: an automated review by the assistant, CI, and the maintainer's approval of each release (#107).
